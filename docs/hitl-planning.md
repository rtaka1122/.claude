## 2. 現状の整理（As-Is）

### 2-1. 対応チャネルと規模

| チャネル | 月間件数 | 現在の対応方法 |
|---------|---------|--------------|
| Gmail | 数十件/月 | 担当者が手動でメール確認・返信 |
| LINE公式アカウント | 数十件/月 | 担当者が手動でトーク確認・返信 |
| FAQ / 自己解決 | なし | WebサイトにFAQなし、LINEにも導線なし |

### 2-2. 現在の対応フロー

```
顧客
  │
  ├─ Gmail / LINE に問い合わせを送信
  │
担当者
  │
  ├─ Step 1: メール / LINE トークを確認（随時・手動監視）
  │           ⏱ 対応漏れリスクあり
  │
  ├─ Step 2: Notion で関連情報を検索
  │           ⏱ 5〜20分（情報が散在しているため）
  │
  ├─ Step 3: 回答文を一から作成
  │           ⏱ 10〜30分
  │
  └─ Step 4: メール / LINE で返信送信
              ⏱ 合計: 1件あたり15分〜1時間以上
```

### 2-3. 課題・ボトルネック

| # | 課題 | 影響 |
|---|------|------|
| 1 | Notionの情報が散在・非構造化 | 検索に時間がかかる。同じ調査を毎回繰り返す |
| 2 | 回答を毎回ゼロから作成 | 担当者の執筆工数が大きい |
| 3 | FAQがない（Web・LINE両方） | 同じ質問が繰り返され、有人対応件数が減らない |
| 4 | 手動監視 | 対応漏れ・遅延リスク |
| 5 | 対応品質が担当者に依存 | 回答のばらつき・属人化 |

## 3. HITLとは何か

### 3-1. 基本概念

**Human-in-the-Loop（HITL）＝「AIが準備、人間が判断・承認」の協調モデル**

```
【HITLの基本構造】

顧客の問い合わせ
      │
      ▼
  ┌────────────────────┐
  │  AI（Claude）が    │  ← 情報収集・下書き生成
  │  ・問い合わせを分析 │
  │  ・ナレッジを検索  │
  │  ・下書き回答を作成 │
  └────────┬───────────┘
           │ 下書き提示
           ▼
  ┌────────────────────┐
  │  担当者が          │  ← 確認・編集・送信判断
  │  ・下書きを確認    │
  │  ・必要に応じて修正│
  │  ・「送信」を承認  │  ★ AIは担当者の承認なしに送信しない
  └────────┬───────────┘
           │
           ▼
       顧客へ返信
```

### 3-2. 3つのモデル比較

| 項目 | 完全手動（現状） | HITL（検討中） | 完全自動化 |
|------|---------------|--------------|----------|
| スピード | 遅い | 速くなる | 最速 |
| 品質保証 | 人間が担保 | 人間が担保 | リスクあり |
| 担当者の工数 | 大きい | 削減できる | 最小 |
| 導入難易度 | — | 中 | 高 |
| 誤回答リスク | 低い | 低い（人間が確認） | 高い |
| MVPに適切か | △（現状維持） | ◎ | ✗ |

### 3-3. なぜ今「完全自動化」はしないのか

1. **ナレッジが未整備** — Notionのデータが散在しており、AIが高精度な回答を出すには構造化が先
2. **品質リスク** — 誤回答が顧客に届くと信頼損失に直結する
3. **学習データ不足** — まずHITLで人間の編集・承認履歴を蓄積することが、将来の自動化の土台になる
4. **チームの習熟** — 担当者がAIの挙動に慣れながら段階的に移行できる

## 4. 検討すべきアプローチの比較

> **この章は「答え」ではありません。MTGで一緒に選択するための選択肢です。**

### Option A: 超シンプルHITL（ノーコード優先）

**概要:** 既存ツール（Gmailの下書き機能 + ノーコード自動化）を最大限活用する

```
Gmail受信
  → n8n / Make（ノーコード）でClaude APIを呼び出し
  → Gmailの「下書き」として回答案を自動生成
  → 担当者がGmailを開いて下書きを確認・編集・送信
```

| 観点 | 評価 |
|------|------|
| 開発コスト | ★★★★★ 最小（ノーコードツールのみ） |
| 担当者の操作変更 | ★★★★★ 最小（Gmailをそのまま使う） |
| カスタマイズ性 | ★★☆☆☆ 低い |
| LINE対応 | ★★★☆☆ 別途対応が必要 |
| 拡張性 | ★★☆☆☆ 複雑化に弱い |
| 向いている状況 | まず動くものを最速で試したい場合 |

**懸念点:** Gmailの下書きはLINEには使えない。チャネルが増えると管理が煩雑になる可能性。

---

### Option B: Notion中心HITL

**概要:** NotionをダッシュボードとナレッジDBの両方として活用する

```
Gmail / LINE受信
  → n8n / Make でClaude APIを呼び出し
  → Notionデータベースに「対応チケット」として下書きを記録
  → 担当者がNotionで確認・承認ボタン押下
  → n8n / Make が承認を検知してGmail / LINEから送信
```

| 観点 | 評価 |
|------|------|
| 開発コスト | ★★★★☆ 比較的小さい |
| 担当者の操作変更 | ★★★☆☆ Notionの操作を覚える必要あり |
| カスタマイズ性 | ★★★☆☆ 中程度 |
| LINE対応 | ★★★★☆ Gmail・LINE両方を統一管理できる |
| 拡張性 | ★★★☆☆ 中程度 |
| 向いている状況 | すでにNotionを使いこなしており、ツールを増やしたくない場合 |

**懸念点:** Notionのデータベース設計が複雑になると管理が大変。Notionのレイテンシ（API速度）が課題になる場合あり。

---

### Option C: 専用ダッシュボード型

**概要:** CS担当者専用のWebアプリを構築し、HITL操作UIを提供する

```
Gmail / LINE受信
  → バックエンドAPI でClaude APIを呼び出し
  → 専用Webダッシュボードに対応チケットが表示される
  → 担当者がダッシュボードで下書き確認・編集・「送信」ボタン押下
  → バックエンドがGmail / LINEから送信
```

| 観点 | 評価 |
|------|------|
| 開発コスト | ★★☆☆☆ 大きい（Webアプリ開発が必要） |
| 担当者の操作変更 | ★★☆☆☆ 新しいツールを覚える必要あり |
| カスタマイズ性 | ★★★★★ 最高 |
| LINE対応 | ★★★★★ 完全統合 |
| 拡張性 | ★★★★★ 高い |
| 向いている状況 | スケール・機能拡張を最初から見据えたい場合 |

**懸念点:** MVPフェーズとしてはオーバーエンジニアリングになる可能性。開発・維持コストが高い。

---

### アプローチ選定のための判断軸

MTGで議論するポイント：

- **スピード重視か、拡張性重視か？**
  → 早く試したい → Option A または B
  → 将来のスケールを見据える → Option C

- **開発リソースはどの程度使えるか？**
  → エンジニア稼働が限定的 → Option A
  → ある程度確保できる → Option B または C

- **担当者のITリテラシーはどの程度か？**
  → Gmailだけで慣れている → Option A
  → Notionを使いこなしている → Option B
  → 新ツールへの抵抗が少ない → Option C

- **まずGmailだけ試したいか、Gmail+LINEを同時に対応したいか？**
  → Gmailだけ → Option A が最速
  → 両方同時 → Option B または C

## 5. HITLの介入ポイント設計（共通）

どのアプローチを選んでも、以下の4つの「人間が介入するタイミング」は共通です。

```
問い合わせ受信
    │
    ▼
[AI] カテゴリ分類・エスカレーション判定
    │
    ├──【介入ポイント①】エスカレーション────────────────────
    │   条件: クレーム、個人情報、金銭、法的内容、判断不能
    │   担当者のアクション: 直接対応 or 上位者にアサイン
    │   ↓（通常ルートはここをスキップ）
    │
[AI] ナレッジ検索
    │
    ├──【介入ポイント②】ナレッジ未ヒット──────────────────
    │   条件: 関連するナレッジが見つからない
    │   担当者のアクション: 手動で情報を補足 or 全文手動作成
    │   ↓（ヒットした場合はここをスキップ）
    │
[AI] 下書き生成
    │
    ├──【介入ポイント③】下書きレビュー・承認 ★最重要★──────
    │   条件: 全件（MVPフェーズは例外なし）
    │   担当者のアクション:
    │     A. そのまま承認 → 送信
    │     B. 一部編集して承認 → 送信
    │     C. 全面書き直し → 送信
    │     D. 保留・エスカレーション
    │
    ▼
送信
    │
    └──【介入ポイント④】フィードバック───────────────────
        条件: 任意（週次バッチでも可）
        担当者のアクション: 良い/悪い回答にタグ付け、Notion更新
```

### エスカレーション判定ルール（案）

| 分類 | 条件例 | 対応方針 |
|------|--------|---------|
| クレーム | 「怒り」「不満」「ひどい」「返金」等のキーワード | 上位者に即アサイン |
| 個人情報 | 住所・口座・パスワードの言及 | セキュリティ担当へ |
| 緊急 | 「今すぐ」「急ぎ」「本日中」等 | 優先度高でキューの先頭へ |
| 判断不能 | AIがカテゴリ分類できない | 担当者が手動分類 |

> **確認事項:** これらのルールは現場の実態に合わせて調整が必要です。上記はあくまで出発点の案です。

## 6. 前提条件の整理（どのアプローチでも必要）

### 6-1. Notionナレッジ整備が最初のボトルネック

```
AIの回答品質 ∝ ナレッジの質

整備されていないNotionデータ → AIの検索精度が低い → 下書き品質が低い
→ 担当者の編集工数が増える → HITLの効果が薄れる
```

**AI導入より先にやること：**

| 優先度 | 作業 | 担当 | 工数概算 |
|--------|------|------|---------|
| 高 | 問い合わせTOP20のFAQをNotionに構造化 | CSチーム | 1〜2週間 |
| 高 | 返品・キャンセルポリシーを正確に文書化 | CSチーム | 3日 |
| 高 | 商品・サービス情報の一覧を整備 | CSチーム | 3日 |
| 中 | クレーム対応ガイドラインを文書化 | CSチーム + 管理職 | 1週間 |
| 低 | 過去の優良対応事例のアーカイブ | CSチーム | Phase 1以降 |

### 6-2. Notionデータの推奨構造

AIが効率よく検索できるよう、以下のデータベース構造を推奨します。

**FAQマスター（最重要）**

| フィールド | 内容例 |
|-----------|--------|
| 質問 | 「返品はできますか？」 |
| 回答 | 「ご購入から30日以内であれば…」 |
| カテゴリ | 返品 / 配送 / 商品 / アカウント / 決済 |
| タグ | 返品, 期限, 条件 |
| 有効フラグ | ✓（古い情報を無効化するため） |
